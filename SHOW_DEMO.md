# Project demonstration

Start with: “My project is an API Documentation Generator. It turns Python API source and usage examples into documentation with source references. A local LLM explains the code, while static analysis preserves declared API facts.”

Show **Bookstore · FastAPI**. The app resolves `app.include_router(book_router, prefix='/v1')` together with the router's `/books` prefix. This explains why the output path is `/v1/books`, even though the handler's decorator contains an empty local path.

Open **POST /v1/books**. Explain `BookCreate` and status 201. In **Source evidence**, show that the handler returns the full saved dictionary. In **Usage examples**, show the POST request and JSON body. Generate the local description and compare it with the source.

In **Request and response fields**, show the required title/author/price fields, title length 1–120, minimum price 0, and published default false. The response adds an integer ID. These tables are extracted from source, so they remain available even when local generation is unavailable.

The header shows model readiness and refreshes every five seconds. If Ollama is stopped or the model is missing, read the setup message and select **Recheck model** after fixing it. The generation controls are disabled while unavailable or busy.

Download OpenAPI and Markdown. Their endpoint contracts and source locations come from analysis; only descriptive prose is generated by Gemma.

Show **Support Tickets · Flask** to demonstrate Blueprint prefix handling and a 201 success-status tuple. Be clear that dynamically read Flask request bodies are not typed schemas in this prototype.

Show **Evaluation**. Explain why the regex baseline misses mounted prefixes, how TF-IDF is calculated, why development data selects the feature setting, and why ten routes/twelve test queries do not support broad accuracy claims.

For the LLM comparison, show `artifacts/llm_comparison.json`. The source-only draft says only an ID is returned, which is wrong. The source/example draft describes the full record. Citation checks alone would not catch that first semantic mistake. This is why the interface keeps original source visible.

Then show **Actual LLM description comparison** on Evaluation: eight endpoints, three sample APIs, sixteen actual outputs. Open a case to compare its source, full generated output and assistant review. Both settings averaged 1.50/2 correctness in this run; context did not consistently remove factual errors. These scores are an assistant assessment, not an independent human study. Use the [three-minute walkthrough](docs/Presentation_Demo.md) and [evaluation method](docs/Evaluation_Method.md) for details.

Likely viva answers:

- **Why an LLM?** It explains behavior and writes a readable reference from supplied code and examples. AST extraction alone provides structure, not a complete prose explanation.
- **Why AST?** Paths, types and status codes are verifiable facts. Deterministic extraction keeps a prose model from silently changing the contract.
- **Why retrieval?** It selects relevant supplied requests and supplies them to the actual LLM prompt. Method/path checks reject requests belonging to another endpoint.
- **What did you implement?** The source workflow, mounting resolution, sparse TF-IDF/cosine calculations, manual metrics, evidence checks, exporters, revision comparison and UI.
- **Did you train Gemma?** No. It is an existing pretrained local model. The project integrates and evaluates its use for this task.
- **What is not proven?** Runtime behavior, completeness on arbitrary projects and broad LLM factuality. The evaluation uses a small, labeled, authored test set.
- **Next step?** Support more frameworks and annotate a larger API dataset with correct contracts and reference explanations for human-reviewed evaluation.
